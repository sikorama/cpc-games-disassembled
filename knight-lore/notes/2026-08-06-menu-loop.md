## Hypothèses à vérifier la prochaine session

1. ~~Rejouer 0x175F pas-à-pas~~ FAIT (voir `notes/2026-08-06-menu-loop.md`,
   section "Trace pas-à-pas via z80_history"). Résultat : hypothèse initiale
   partiellement révisée, voir ci-dessous.
2. Identifier 0x16DA (appelée 6× depuis la boucle du menu). **FAIT** :
   0x16DA n'est pas un `call` à une adresse fixe mais du code inline —
   `PUSH HL / LD HL,3294 / LD (008C),HL / POP HL / CALL 3186` : fixe la base
   de la table de formes à 0x3294 puis appelle 0x3186 (calcul d'adresse,
   voir routine ci-dessous), donc "6DA" et "3186" sont deux routines
   distinctes à documenter séparément.
3. Dump des tables 0x167B/0x1681/0x168D : fait partiellement (voir
   ci-dessous), à corréler avec le rendu réel des 6 icônes.
4. Mode graphique GA pendant le menu : **FAIT** — `mode=1` (2bpp, 4 couleurs
   actives), confirmé via `emu_state().ga`. Le buffer destination de
   0x170D (0xB7D6) est en RAM bank 2 (région 0x8000-0xBFFF), **hors zone
   écran** (écran = bank 3, 0xC000-0xFFFF) — donc PAS un rendu direct à
   l'écran, plutôt un buffer de travail intermédiaire (masque/forme
   pré-calculée).
5. Une fois en jeu : nouveau relevé de codemap pour capturer le moteur de
   rendu isométrique et la boucle de jeu principale. **Toujours à faire.**

## Trace pas-à-pas via z80_history (révision de l'hypothèse 0x170D)

Méthode : breakpoint sur 0x175F, resume, puis N×`z80_step` suivi d'un seul
`z80_history` (l'historique de l'émulateur donne l'ordre exact et l'état
après chaque instruction — bien plus fiable qu'un polling manuel PC+step
qui peut désynchroniser l'affichage d'un cran).

Séquence observée pour un octet source donné (A=0x14 en entrée) :
- Adresse source = `(0x008C) + A×8` = `0x3294 + 0xA0` = `0x3334`.
- Octet lu à 0x3334 = `0xE4`.
- `RRCA` ×4 (rotation complète = swap des deux nibbles) → `0x4E`.
- `AND 0x0F` → `0x0E` (= 14 = **nibble HAUT de l'octet source**, extrait par
  rotation+masque plutôt que par un simple `AND F0` puis shift — choix de
  code un peu détourné mais fonctionnellement équivalent).
- Écrit dans `C` puis combiné avec le nibble bas (lu séparément, second
  `LD A,(DE)` sans avancer DE entre les deux lectures) pour reconstituer un
  octet complet écrit à `(HL)`.

**Révision de l'hypothèse "police de caractères"** : le buffer destination
observé (`0xB7D6`) est situé en RAM bank 2 (région 0x8000-0xBFFF), **hors
zone écran** (écran CPC standard = bank 3, 0xC000-0xFFFF). Donc 0x170D
n'écrit *pas* directement à l'écran — c'est un buffer de travail
intermédiaire. Par ailleurs, le contenu de la table source à 0x3294
(dumpée sur 128 octets) commence par `38 6C D6 D6 D6 D6 6C 38` — lu comme
bitmap 1bpp classique (8 octets = 8 lignes de 8 pixels), ça dessine un
**losange/cercle symétrique**, pas un caractère alphanumérique. Nouvelle
hypothèse : cette table décrit des **pictogrammes/icônes 8×8** (les 6
icônes de méthode de contrôle affichées au menu), et 0x170D **déballe un
nibble par pixel-paire** — cohérent avec une conversion de bitmap 1bpp
(façon ZX Spectrum) vers un format 2bpp/4-couleurs exploitable en Mode 1
CPC. **Hypothèse forte mais non encore confirmée** : ce pourrait être
littéralement la **couche de compatibilité de conversion de pixels
Speccy→CPC** évoquée en intro de ce projet (ce qui expliquerait le coût
CPU et le rendu moins soigné). À confirmer en :
- dumpant le buffer 0xB7D6 en entier après un cycle complet des 8 lignes,
  et en le comparant visuellement (via `screenshot`) à l'icône affichée à
  l'écran pour la même itération de boucle ;
- vérifiant si cette même routine (0x170D) est réutilisée ailleurs, en jeu,
  pour le rendu des sprites/tuiles isométriques (ce qui confirmerait
  qu'il s'agit d'une routine générique de conversion, pas spécifique au
  menu).

## CONFIRMÉ : 0x170D est le moteur de rendu de texte (pas des icônes)

Poursuite du traçage (breakpoint sur 0x170D + lecture de l'adresse de
retour sur la pile, répété 8×) : le call revient systématiquement à
`0x1706`, qui est bien `CALL 0x170D` situé à `0x1703` (3 octets, retour
= 0x1703+3). Désassemblage du contexte englobant (`0x16E5-0x170D`) :

```
16E5  3A7C00     ld     a,(007C)
16E8  180D       jr     16F7
16EA  E5         push   hl
16EB  219432     ld     hl,3294
16EE  228C00     ld     (008C),hl
16F1  E1         pop    hl
16F2  CD8631     call   3186
16F5  1A         ld     a,(de)
16F6  13         inc    de
16F7  322C17     ld     (172C),a
16FA  323C17     ld     (173C),a
16FD  1A         ld     a,(de)      ; <- boucle : lit le prochain octet de la chaîne
16FE  13         inc    de
16FF  CB7F       bit    7,a         ; bit 7 = marqueur fin de chaîne (style ZX Spectrum)
1701  2005       jr     nz,1708     ; si bit7=1 -> dernier caractère
1703  CD0D17     call   170D        ; caractère normal : rendre le glyphe
1706  18F5       jr     16FD        ; boucle
1708  E67F       and    7F          ; dernier caractère : masquer le bit7
170A  C30D17     jp     170D        ; rendre le dernier glyphe puis RET (fin de chaîne)
```

**Conclusion : c'est un afficheur de chaîne de caractères classique**, DE
pointant vers une chaîne où le dernier octet a son bit 7 positionné comme
terminateur (convention héritée du ZX Spectrum). Chaque caractère est
rendu via `CALL 0x170D` qui va chercher le glyphe correspondant dans la
table de police à `0x3294` (via `0x3186`, cf. ci-dessous) et le déballe
dans un buffer de travail.

**Révision de l'hypothèse "icônes des 6 méthodes de contrôle"** : la
boucle de 6 itérations vue en `0x175F-0x1786` (section précédente) appelle
très probablement cette routine de texte 6 fois pour dessiner les
**libellés textuels** des 6 options du menu (pas des pictogrammes) — donc
"table1/2/3" (0x167B/0x1681/0x168D) sont vraisemblablement des pointeurs
vers 6 chaînes de texte différentes plutôt que des index d'icônes.

## 0x3186 — Calcul d'adresse destination (CONFIRMÉ par désassemblage direct)

```
3186  C5         push   bc
3187  CB3C       srl    h
3189  CB1D       rr     l
318B  CB3C       srl    h
318D  CB1D       rr     l
318F  010090     ld     bc,9000
3192  09         add    hl,bc
3193  C1         pop    bc
3194  C9         ret
```
Soit `HL = (HL >> 2) + 0x9000`. Vérifié : avec HL=0x9F58 en entrée, calcul
donne bien 0xB7D6 (0x9F58>>2 = 0x27D6 ; +0x9000 = 0xB7D6), exactement la
valeur observée dans la trace précédente. **Ce n'est donc pas un calcul de
base de table de forme, mais un calcul d'adresse dans un buffer de
travail** dont la taille utile est 1/4 de l'espace source — cohérent avec
un buffer de glyphes déballés en 2bpp (4 valeurs/octet) à partir d'une
source qui encode 4 pixels/octet (format 4bpp source vu dans 0x170D).

## Hypothèse retenue : couche de compatibilité Speccy → CPC

L'utilisateur avait anticipé que le menu réutiliserait des routines
similaires à celles du jeu lui-même pour l'affichage — cohérent avec ce
qu'on observe : 0x170D fait de la conversion bit à bit typique d'un
portage (rotation + masquage pour extraire des nibbles), le genre de code
qui coûte du temps CPU comparé à un rendu natif CPC (qui utiliserait
directement le format mémoire écran du Gate Array sans étape de
conversion). **Hypothèse toujours à confirmer en jeu** : si le moteur de
rendu isométrique (sprites des pièces, joueur) réutilise 0x170D ou une
routine sœur avec la même signature (déballage nibble + table de forme +
calcul d'adresse ÷4), ce sera la preuve que c'est une routine générique de
conversion de bitmap, embarquée depuis le code ZX Spectrum d'origine.
